## 0.8.0

### Minor Changes

- [#88](https://github.com/mfeflow/mfeflow/pull/88) [`d7e7ec2`](https://github.com/mfeflow/mfeflow/commit/d7e7ec2f9d5813ef42efe9aea68f5de4475def01) Thanks [@speedsharmaai](https://github.com/speedsharmaai)! - `mfeflow init --kind remote` makes one repo of one or more remotes with no shell, for a team that joins a platform whose shell is deployed from another repo. `mfeflow.json` has `repo: "remote"` and `topology: "monorepo"`, `apps` holds only remotes, and there is no `registry/` folder. `--remotes` needs at least one name (default `catalog`; `none` is E107). `--shell <url|file>` records where the deployed shell is, as a new optional `shell` field of `mfeflow.json` that follows the rules of `--against` (https, or http on localhost, or a file; no credentials or token in a URL); `doctor` and `check-compat` use it when `--against` is not given, so the "shell is not in this repo" warning goes away. `dev` runs the remotes and, with a recorded shell, prints how to see one in that shell and that overrides work only in a development build. `add remote` writes no route and no registry entry in such a repo, and `upgrade` does not bring a shell or registry folder back. Features write their remote parts and skip their shell parts. `pnpm create mfeflow` takes the same flags.

- [#80](https://github.com/mfeflow/mfeflow/pull/80) [`9cd08ea`](https://github.com/mfeflow/mfeflow/commit/9cd08eaf684dc3155de4bb43db89a89099d735ba) Thanks [@speedsharmaai](https://github.com/speedsharmaai)! - `mfeflow init --kind tooling` makes a repo with no apps: the platform template (`contracts` and `tokens` packages, reusable CI, Renovate preset, Changesets) as its own repo, with `repo: "platform"`, `topology: "monorepo"` and `apps: {}` in `mfeflow.json`. `--features` takes `lint-oxlint`, `git-hooks`, `commit-prompt` and `release`; anything with an app part, and `ci-github` (it would replace the repo's own `ci.yml`), is refused with E107 naming the feature. `--kind` is `app` by default, and `remote` answers "not available in this release". In a project with no apps, `dev`, `budget`, `validate`, `check-compat` and `upgrade` print one line and exit 0, and `doctor` adds that line above its report. The `platform/` repo of a polyrepo now gets the root-only features chosen at `init` (`lint-oxlint`, `git-hooks`, `commit-prompt`), and is unchanged otherwise. The `repo` field of `mfeflow.json` is described again: absent means an app repo, and a platform repo may have no apps at all.

- [#79](https://github.com/mfeflow/mfeflow/pull/79) [`794306c`](https://github.com/mfeflow/mfeflow/commit/794306c01ebc3c7305606094f8fd00b7036d7160) Thanks [@speedsharmaai](https://github.com/speedsharmaai)! - `mfeflow init --remotes none` (or `--remotes ""`, or `"remotes": []` in a preset) starts a project with only a shell, in a monorepo and in a polyrepo. Without the flag `init` still makes `catalog,cart`. At the prompt an empty answer means none, and `none` mixed with names is E107. `mfeflow dev` prints a line saying so before it starts the shell, and the route table of a shell-only project is written so that Prettier leaves it alone. Before this, `--remotes ""` was read as not given and `--remotes none` created a remote called `none`.

- [#81](https://github.com/mfeflow/mfeflow/pull/81) [`58c9bab`](https://github.com/mfeflow/mfeflow/commit/58c9bab67a3578a4fbf68af8c41c4d6bf81e3c50) Thanks [@speedsharmaai](https://github.com/speedsharmaai)! - A feature that needs an app and is asked for in a tooling repo now fails with its own error, `MFEFLOW_E216` ("A feature needs an app, and this repo has none"), instead of the general E107. The message names the feature and the part that goes to an app, and says to use a repo with apps; the exit code is still 2. `ci-github` keeps E107, because its problem is the `ci.yml` the repo already has, not that it needs an app. The docs list the four features a repo with no apps takes.

- [#83](https://github.com/mfeflow/mfeflow/pull/83) [`277d79a`](https://github.com/mfeflow/mfeflow/commit/277d79a13ccf4a920be3fb7516604f7132536d89) Thanks [@speedsharmaai](https://github.com/speedsharmaai)! - `mfeflow init --kind tooling --packages` can also make `analytics`, `telemetry`, `http`, `theme`, `url-factory` and `storage` in your scope. Each depends on our package of the same name, re-exports its API, and adds your defaults and one helper: `analytics` has consent denied until granted, a Tag Manager container id per environment and `createAnalytics(env)`; `telemetry` has the collector address per environment, a service name prefix and `telemetryOptions(env, service, version)`; `http` has base URLs per environment, one place for token handling and `createHttp(endpoints, env)`; `theme` has your light and dark tokens in one file and `createThemes()`. `http` also makes `url-factory` and `theme` also makes `storage`, and the output says so. The wrappers hold settings only, never state, because a package in your scope is not shared between the shell and the remotes by name.

- [#84](https://github.com/mfeflow/mfeflow/pull/84) [`f7bc75b`](https://github.com/mfeflow/mfeflow/commit/f7bc75b2fe1447fbf10c726cc9c2b7af56957263) Thanks [@speedsharmaai](https://github.com/speedsharmaai)! - `mfeflow init --kind tooling --packages` can also make `i18n`, `event-bus`, `route-factory`, `runtime` and `testing` in your scope, so every shared package except `contracts` and `tokens` (which a tooling repo already has) is a choice. `i18n` has your languages, the default language and the namespace list, with `startI18n()`; `event-bus` has your shared events declared in one file and `configureCompanyEvents()`; `route-factory` has your routes and `createCompanyLinks()`; `runtime` has the registry addresses per environment and `loadRegistry(env)`; `testing` has your providers and `renderWithCompany()`. `i18n` also makes `storage`, `route-factory` also makes `url-factory` and `testing` also makes `runtime`, and the output says so. `runtime` and `testing` are for micro-frontends and the output says that too. Each carries the peer dependencies of our package of the same name, so a missing `i18next` or `react` shows as a peer warning.

- [#82](https://github.com/mfeflow/mfeflow/pull/82) [`6824ffe`](https://github.com/mfeflow/mfeflow/commit/6824ffe8e89fff3921215080e624e6a8859aea95) Thanks [@speedsharmaai](https://github.com/speedsharmaai)! - `mfeflow init --kind tooling --packages a,b` makes one package for each name in your scope, in `packages/<name>/` of the tooling repo (a multiselect asks when it runs interactively, and a preset can carry `packages`). This release has `tsconfig` and `oxlint-config`, and both are made when the flag is left out. `@<scope>/tsconfig` has `base`, `react-app`, `react-library` and `node` presets that extend `@mfeflow/tsconfig`. `@<scope>/oxlint-config` writes `dist/oxlintrc.json` from `@mfeflow/oxlint-config` and your `overrides.json` when you build, because oxlint does not resolve a package name in `extends`. An unknown name is `MFEFLOW_E107` and lists the valid ones; `--packages` without `--kind tooling` is E107. A package that needs another adds it and the command says so.

- [#76](https://github.com/mfeflow/mfeflow/pull/76) [`cc9b8d2`](https://github.com/mfeflow/mfeflow/commit/cc9b8d2ffb44c6f4ff28db3cc67fb8e876a97114) Thanks [@gioboa](https://github.com/gioboa)! - Vite as an alternative to Rsbuild. `mfeflow init --bundler vite` (or `"bundler": "vite"` in a preset) builds every app with Vite and `@module-federation/vite`, through the new `@mfeflow/vite` presets, which take the same options as `@mfeflow/rsbuild`. Both presets now build on `@mfeflow/bundler-shared`, so a Vite app shares the same singletons, manifest and runtime plugins; `@mfeflow/rsbuild`'s API is unchanged. `mfeflow.json` records the choice in an optional `bundler` field (absent means Rsbuild), and feature manifests can test it with a `project:bundler` condition. The theming, env-t3, tsconfig, storybook, deploy-docker and deploy-cloudflare features write the Vite variant of their files. `mfeflow upgrade --bundler vite` moves an existing project and removes the Rsbuild config, dependencies and scripts you did not change. `mfeflow adopt` reads Vite configs that use `@module-federation/vite`, the runtime-plugin check reads `vite.config.ts`, and `mfeflow budget` counts the modules a Vite shell preloads.

## 0.6.0

### Minor Changes

- [#65](https://github.com/mfeflow/mfeflow/pull/65) [`2fc1be2`](https://github.com/mfeflow/mfeflow/commit/2fc1be21fd211e04e5301d04deb218832b0fbab5) Thanks [@speedsharmaai](https://github.com/speedsharmaai)! - You can now give each team its own repo. `mfeflow init my-org --topology polyrepo --remotes catalog,cart` creates a folder with a platform repo, a shell repo and a repo for each remote. Each one is a separate git repo with its own `mfeflow.json`.
  
  The platform repo holds two shared packages, published with Changesets, a reusable GitHub Actions workflow that every other repo calls, and a Renovate preset. The shell and the remotes install those packages from `link:` paths, so a first run needs no registry. The docs list the options for publishing them (npm, GitHub Packages, a private registry). mfeflow writes the repos on your machine and never calls GitHub; creating them there is your job.
  
  `mfeflow add team-repo checkout`, run in the shell repo, adds one more remote repo next to the others and registers it in the shell. The shell finds its remotes in `devRemotes` in `public/config/runtime-config.dev.json`, so `mfeflow dev` in the shell repo works with remotes that run from other repos. `mfeflow validate` and `doctor` know which repo they are in, and a platform repo may have no shell in `mfeflow.json`.
  
  `--org` sets the GitHub owner the generated CI and Renovate files point at; it defaults to the scope without the `@`. If `git init` cannot run in a repo, `init` warns and names it instead of failing.
  
  The `core` template moved to 0.5.0 because the shell's `rsbuild.config.ts` reads its dev remotes from config in a polyrepo. A monorepo gets the same file as before. `ci-github` and `env-t3` cannot be used in a polyrepo yet. `hybrid` is still not available.

## 0.1.0

### Minor Changes

- [#19](https://github.com/mfeflow/mfeflow/pull/19) [`3fb82a3`](https://github.com/mfeflow/mfeflow/commit/3fb82a3ae0c2fb6d3ecb610a252ad8a659066458) Thanks [@speedsharmaai](https://github.com/speedsharmaai)! - `mfeflow init`, `add remote`, `add shell`, `add <feature>` and `features`, and `npm create mfeflow@latest`, which runs `init`.
  
  `init` writes a pnpm 12 workspace with Turborepo, a shell and remotes (default `catalog` and `cart`) as thin configs over `@mfeflow/rsbuild`, a registry per environment, and the first-party features `core`, `tsconfig`, `lint-oxlint`, `url-factory` and `git-hooks`. `pnpm dev` in the result starts the shell and every remote, with a dev registry pointing at their dev servers. Every command takes `--yes`, `--preset`, `--json` (schema-checked output), `--dry-run` (summary and diff, nothing written), `--cwd`, `--no-install` and `--verbose`; errors print `MFEFLOW_Exxx`, a fix and a docs link, with stable exit codes. `--local <checkout>` links `@mfeflow/*` from a built clone so a project can be generated and run before anything is on npm.
  
  `@mfeflow/core` exports `inOrder`, `hasErrno` and `messageOf`, gives templates `app.port`, lets a `PlanBuilder` rewrite dependency ranges (`rewriteRange`), and adds the error codes `E107` to `E110` and `E215`. `@mfeflow/contracts` accepts an optional `port` on each app in `mfeflow.json`.
  
  Migration: app and remote names (`MFE_NAME` in `@mfeflow/contracts`) are now lowercase words of letters and digits joined by single underscores, such as `order_history`. A name that ends in `_`, has `__`, or has `_` before a digit (`cart_`, `a__b`, `a_1`) is refused, because it would produce the same route component as another name; rename the app and its `mfe.json` and `registry` entry. `@mfeflow/core` also exports `readCappedText`, the size-capped body reader `fetchRemoteText` uses.
  
  Registry URL templates may contain `{version}`; `add shell` and `add remote` use it to fetch each installed registry feature at the version `mfeflow.json` recorded, refuse when the registry serves another one, and ask for the same confirmation as `add <feature>`.
